# 개찰결과 최초 공개 알림

기존 workflow_dispatch(외부 약 2분 호출), 발주계획·사전규격·입찰공고 검색 범위와 ntfy 채널을 유지한다. 최종 낙찰자 확정은 추적하지 않는다.

## 추적과 발송

- `notices.stage='입찰공고' AND notified=1`인 기존 발송 완료 이력만 `opening_watch`로 누적한다. 공고번호와 정규화한 차수(000)가 키이며 다른 차수는 합치지 않는다.
- 마감 전에는 조회하지 않는다. 공개 화면의 개찰완료·유찰·재입찰 결과만 받아 동일 공고번호와 차수를 검증한다. 첫 공개 결과를 알린 뒤 해당 키의 추적은 종료한다.
- 결과를 SQLite에 먼저 기록하고 ntfy 성공 시 발송 완료를 기록한다. 실패하면 결과를 재조회하지 않고 다음 실행에서 재전송한다.
- 발송 전 ntfy 보관 이력의 `개찰키:공고번호:차수`를 확인한다. 응답 유실이나 DB push 실패 후에도 수신 이력이 있으면 재전송하지 않는다. 이력 조회가 실패하면 발송을 연기한다.
- SQLite는 기존 nara 전용 `scripts/persist_state.py`로 저장한다. 동일 DB의 동시 변경을 덮어쓰지 않는 기존 충돌 검증과 Actions 실행 직렬화를 유지한다. 취소·실패 시 복구 DB artifact도 보관한다.

## 부하와 지연

- 기존 알림 검사가 우선이다. 그 뒤 실행당 최대 8건, 동시 최대 4건을 조회한다. 공공데이터 API 추가 호출은 0건이다. 나라장터 공개 화면은 공고당 세션 초기화 1회와 목록 조회 1회, 결과가 있으면 직접 링크 검증 1회를 사용한다. ntfy 이력 조회는 실행당 1회다.
- 최근 마감 건은 120초 후, 마감 7일이 지난 미공개 건은 900초 후 다시 조회한다. 대기열 순환으로 장기 미공개 건도 버리지 않는다. 조회 건수가 한도를 넘으면 다음 실행에서 이어서 처리한다. 따라서 외부 호출 간격이 2분이어도 최초 이관·대기열·나라장터 장애·Actions 대기시간에 따라 알림은 더 늦어질 수 있다.
- 전송은 25초 처리 예산 안에서만 시작한다. 네트워크 요청별 연결·응답 제한을 두어 장기 대기를 줄인다. 이미 시작한 조회는 종료까지 기다린다.
- ntfy와 Git에는 하나의 원자적 트랜잭션이 없으므로, 발송 뒤 상태 저장이 유실되고 ntfy 보관 이력까지 만료된 경우의 절대적인 exactly-once는 보장할 수 없다. 정상 실행과 보관 이력 내 복구는 영속 키와 수신 이력으로 중복을 억제한다.
- 나라장터 공개 결과 목록에 노출되지 않는 외부기관·민간 결과는 임의 링크나 낙찰 추정으로 알리지 않고 계속 대기한다.
